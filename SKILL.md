# Minecraft Plugin Craft

Это не туториал и не сборник рецептов. Это набор инженерных решений, принятых заранее, чтобы не принимать их плохо в спешке.

Правило над правилами: **если не можешь объяснить, зачем строка существует — её не должно быть.**

Три вопроса к любому куску кода:
1. Что сломается, если это удалить?
2. Кто это прочитает через полгода и что подумает?
3. Сколько раз в секунду это выполняется?

## 0. Стек и базовые решения

| Что | Выбор | Почему |
|---|---|---|
| Платформа | Paper, `paper-plugin.yml` | Spigot API беднее, Bukkit — археология |
| Folia | поддерживать, если проект для сети | ретрофит стоит в 5 раз дороже |
| Java | 21 LTS | records, sealed, pattern matching, virtual threads |
| Сборка | Gradle Kotlin DSL + `paperweight-userdev` | типобезопасно, Mojang-mapped рантайм |
| Тексты | Adventure `Component` + MiniMessage | `ChatColor` и `§` — легаси |
| Конфиг | Configurate или свои `record`-POJO | «строка по ключу» — источник багов |
| БД | HikariCP + JDBC, миграции Flyway | ORM для плагина обычно избыточен |
| Тесты | JUnit 5, AssertJ, MockBukkit точечно | не гоняем сервер ради формулы |
| Качество | Spotless, ErrorProne, NullAway | баги ловит компилятор, не ревьюер |

Отклоняешься от стека — одна строка обоснования в PR-описании. Не в коде.

### Что означает «поддерживать версию»
Заявленная версия — та, на которой прогнан ручной сценарий и зелёный CI. Не «должно работать». Строка «1.8–1.21» в описании плагина — признак несерьёзного проекта.

## 1. Работа с API

### Источник истины
Порядок обращения, строго сверху вниз:

1. **Декомпилированные исходники джара из твоего classpath.** IDE → Decompile. Единственное, что не врёт.
2. Paper Javadoc — `jd.papermc.io`, ровно твоей версии.
3. Исходники Paper на GitHub, включая patches и обсуждения PR — там семантика, которой нет в Javadoc.
4. `docs.papermc.io`, `docs.advntr.dev`.
5. Minecraft Wiki — по игровым механикам, не по API.
6. Discord PaperMC `#paper-dev` — тонкие вопросы.
7. SpigotMC / StackOverflow — **гипотеза**, требующая проверки в п.1. Большая часть ответов там из 1.8.

Никогда не изобретай сигнатуру «по логике имени». Несуществующий метод — самый узнаваемый признак сгенерированного кода.

### Границы платформы

**NMS изолируется за интерфейсом. Всегда.**

```java
public interface EntityBridge {
    void sendFakeEquipment(Player viewer, LivingEntity target, ItemStack item);
}
```

Одна реализация, одна точка версионной проверки, остальной код о существовании NMS не знает. NMS, размазанный по двенадцати классам, убивает проект на следующем релизе Minecraft.

**Reflection — последний аргумент.** Если применяешь — резолви один раз в статическом инициализаторе и храни `MethodHandle`:

```java
private static final MethodHandle GET_HANDLE = resolveGetHandle();
```

Не `getDeclaredMethod` внутри тика. Это в сотни раз медленнее и падает молча.

**Проверка зависимостей** — через `ServicesManager` или `PluginManager`, не через `try { Class.forName(...) } catch (Throwable ignored) {}`.

**`@Deprecated` в Bukkit** обычно значит «работает не так, как ты думаешь, и скоро исчезнет». Используешь — пиши почему в PR.

### Жизненный цикл

| Фаза | Что можно | Что нельзя |
|---|---|---|
| `onLoad` | worldgen, флаги, регистрация до миров | обращение к мирам и игрокам |
| `onEnable` | регистрация, старт пулов, async-загрузка | блокирующий I/O, тяжёлые вычисления |
| `onDisable` | быстрый синхронный flush | планирование задач, async-сохранение |

`onDisable` вызывается на гасящемся сервере: шедулер уже мёртв, async-сохранение не успеет. Данные, которые нельзя потерять, сохраняй периодически и по событию, а не только при выключении.

### Утечки, которых не должно быть
Не храни в долгоживущих структурах: `Player`, `Entity`, `World`, `Block`, `Chunk`, `Inventory`.
Храни `UUID`, `Location`-снимок, упакованный ключ чанка.

```java
// плохо — держит объект игрока после выхода, течёт весь мир за собой
private final Map<Player, Session> sessions = new HashMap<>();

// хорошо
private final Map<UUID, Session> sessions = new HashMap<>();
```

Чисти по `PlayerQuitEvent`. Кеш без стратегии очистки — это утечка, которая ещё не проявилась.

### События

**Приоритеты по смыслу:**

| Приоритет | Роль |
|---|---|
| `LOWEST` / `LOW` | подготовка, модификация входных данных |
| `NORMAL` | основная логика |
| `HIGH` / `HIGHEST` | решающее слово, финальная отмена |
| `MONITOR` | **только чтение**, никаких изменений и отмен |

`ignoreCancelled = true` по умолчанию для реактивных обработчиков.

**Горячие события** (`PlayerMoveEvent`, `BlockPhysicsEvent`, `EntityDamageEvent`, `InventoryClickEvent`) — десятки тысяч вызовов в секунду. Первой строкой — дешёвый выход:

```java
@EventHandler(ignoreCancelled = true)
public void onMove(PlayerMoveEvent event) {
    if (!event.hasChangedBlock()) return;
    ...
}
```

Не отменяй событие «на всякий случай»: отмена — контракт с другими плагинами, и её видят все.

Отписывайся (`HandlerList.unregisterAll`) при выгрузке модуля, иначе после `/reload` слушатели дублируются.

## 2. Анти-слоп

Слоп — код, синтаксически корректный и семантически пустой. Он не обязательно сгенерирован машиной, но выглядит именно так.

### Удалить безусловно

```java
// плохо
/**
 * Gets the player.
 * @return the player
 */
public Player getPlayer() {
    // получаем игрока
    return this.player;
}

// ===================== UTILS =====================

// TODO: implement later
```

Список на удаление:
- комментарии, пересказывающие следующую строку;
- Javadoc-заглушки, не добавляющие информации;
- баннеры-разделители и ASCII-арт;
- эмодзи в логах и в исходниках;
- `// TODO` в смёрдженном коде — либо сделано, либо задача в трекере;
- геттер-обёртка над полем, которое никто не переопределит;
- абстракция «на будущее»: интерфейс с одной реализацией, фабрика фабрик;
- `Utils`, `Helper`, `Manager`, `Handler`, `Common`, `Misc`, `Data`, `Info` в именах — это не имена, это отказ от именования;
- `ItemBuilder` на 400 строк, из которых используется четыре метода.

### Комментарий имеет право на жизнь, если объясняет *почему*

```java
// Paper дросселирует физику TNT при >64 сущностях в чанке — отсюда батч по 32
// см. PaperMC/Paper#9431
// порядок важен: инвентарь закрывается до апдейта, иначе клиент рассинхронится
```

### Как код становится человечным

**Ранний выход вместо лестницы.**

```java
// плохо
public void buy(Player player, ShopItem item) {
    if (player != null) {
        if (item != null) {
            if (economy.has(player, item.price())) {
                if (hasSpace(player)) {
                    economy.withdraw(player, item.price());
                    give(player, item);
                }
            }
        }
    }
}

// хорошо
public void buy(Player player, ShopItem item) {
    if (!economy.has(player, item.price())) {
        messages.send(player, "shop.not-enough", item.price());
        return;
    }
    if (!hasSpace(player)) {
        messages.send(player, "shop.inventory-full");
        return;
    }
    economy.withdraw(player, item.price());
    give(player, item);
}
```

Ошибочные ветки — короткие и наверху. Счастливый путь — внизу, без отступов.

**Имена из доменного языка.** `withdrawBalance`, `cooldownRemaining`, `isOnCooldown`, `refundTransaction`. Не `data`, `temp`, `result2`, `flag`, `obj`, `doStuff`.

**Булевы читаются как утверждение:** `if (player.isOnCooldown())`, не `if (checkCooldown(player) == true)`.

**Локальная переменная вместо комментария:**

```java
boolean shouldRefund = !event.isCancelled() && transaction.isReversible();
if (shouldRefund) { ... }
```

**Разнообразие форм — признак живого автора.** Где-то `switch`-выражение, где-то ранний `return`, где-то стрим. Идеально однородный код на 3000 строк — машинный.

**Неровности допустимы.** Один метод длиннее остальных, потому что дробить его — врать про структуру задачи. Симметрия ради симметрии хуже честной асимметрии.

### Три теста на слоп

1. **Тест удаления комментариев.** Убери все комментарии из файла. Стало непонятнее? Верни только те, что были нужны. В 90% случаев не станет.
2. **Тест вслух.** Прочитай метод вслух как предложение. Спотыкаешься — переименуй.
3. **Тест «зачем».** Ткни в случайный класс и спроси, какую проблему он решает. Нет ответа за 5 секунд — класс лишний.

## 3. Архитектура проекта

```
com.example.shop
├── ShopPlugin.java          точка входа: только проводка зависимостей
├── command/                 парсинг ввода → вызов домена, ноль бизнес-логики
├── listener/                тонкие адаптеры событий к домену
├── domain/                  сущности и правила. БЕЗ импортов Bukkit
│   ├── Shop.java
│   ├── Transaction.java
│   └── PricingPolicy.java
├── storage/                 интерфейс репозитория + реализации
│   ├── ShopRepository.java
│   ├── SqlShopRepository.java
│   └── migration/
├── config/                  типизированные record-POJO
├── text/                    Messages, форматирование, MiniMessage
└── platform/                NMS/Folia-мосты за интерфейсами
```

**Главное правило: `domain/` не импортирует Bukkit.** Следствия — логика тестируется за миллисекунды без сервера, правила читаются как правила, проект переживает смену платформы.

### Проводка

```java
public final class ShopPlugin extends JavaPlugin {

    private ShopRepository repository;

    @Override
    public void onEnable() {
        ShopConfig config = ShopConfig.load(getDataFolder().toPath());
        Messages messages = Messages.load(getDataFolder().toPath());

        repository = SqlShopRepository.create(config.database());
        ShopService service = new ShopService(repository, config.pricing());

        getServer().getPluginManager()
            .registerEvents(new ShopListener(service, messages), this);
    }

    @Override
    public void onDisable() {
        if (repository != null) repository.close();
    }
}
```

Зависимости — через конструктор. `getInstance()`-синглтон допустим только для самого плагина, и лучше без него: статический доступ прячет граф зависимостей и ломает тесты.

### Правила проекта
- Один класс — одна причина для изменения. `ShopPlugin` не знает про SQL.
- Нет мёртвого кода. Закомментированный блок «пусть полежит» удаляется — есть git.
- Третье повторение = извлечение. Первое и второе — терпим, преждевременная абстракция дороже дубля.
- README для человека, впервые открывшего проект: что делает, как собрать, как настроить. Без маркетинга и без списка «✨ Features».
- Коммиты осмысленные: `fix: откат баланса при отмене транзакции`. Не `update`, не `fix bug`, не `.`.
- CHANGELOG пишется для админа сервера, а не для тебя.

## 4. Команды

Не парси `String[] args` вручную в каждой команде. Используй Brigadier (Paper `LifecycleEventManager`) или Cloud — получишь типы, автодополнение и внятные ошибки бесплатно.

Обязательное для любой команды:

```java
// 1. Права проверяются до любой работы
if (!sender.hasPermission("shop.admin.reload")) { ... }

// 2. Разделены отправитель-игрок и отправитель-консоль
if (!(sender instanceof Player player)) { ... }

// 3. Аргументы валидируются с границами
int amount = parsePositiveInt(args[0], 1, 64);

// 4. Тяжёлая работа — async, ответ — в main
```

- Все ответы — из `messages.yml`, включая usage.
- Автодополнение фильтруется по правам: игрок не должен видеть админские подкоманды.
- Rate limit на дорогие команды (поиск, отчёты, генерация).
- Confirmation для разрушительных действий (`/shop wipe` → `/shop wipe confirm`), с TTL подтверждения.
- Не регистрируй команды динамически через `CommandMap`, если можно объявить их в манифесте.

## 5. GUI и инвентари

Самое частое место дюпов и уязвимостей.

- **Отменяй событие первым делом**, потом обрабатывай: `event.setCancelled(true)` до любой логики.
- Обрабатывай **все** пути перемещения: `InventoryClickEvent`, `InventoryDragEvent`, shift-click, `NumberKey`, `SwapOffhand`, `InventoryMoveItemEvent`.
- Идентифицируй меню по holder-объекту, **не по заголовку**:

```java
if (!(event.getInventory().getHolder() instanceof ShopHolder holder)) return;
```

Заголовок подделывается и локализуется, holder — нет.
- Проверяй `event.getClickedInventory()` — клик мог быть по инвентарю игрока, а не по меню.
- Права проверяются в обработчике клика. Скрытая кнопка не является проверкой прав.
- Дебаунс: два клика за тик = одна покупка. Иначе двойная покупка на лаге.
- Не перерисовывай меню каждый тик. Обновляй по событию изменения данных.
- `Component`-компоненты меню собери один раз и переиспользуй — они иммутабельны.
- Закрытие меню при перезагрузке плагина: висящий инвентарь с мёртвым holder — источник NPE.

## 6. Хранение данных

### Выбор
- **PDC (`PersistentDataContainer`)** — данные, привязанные к предмету/сущности/чанку. Ключи с namespace плагина. Не пихай в PDC килобайты JSON.
- **SQLite** — одиночный сервер.
- **MySQL / PostgreSQL** — сеть серверов.
- **Плоские файлы** — только конфиг и то, что редактирует человек. Не база игроков.

### Правила
- Соединения — через HikariCP, размер пула считанный (обычно 4–10), не 100.
- Запросы — **только** `PreparedStatement`.
- Массовые вставки — `addBatch()` / `executeBatch()`, не цикл `execute()`.
- Схема версионируется миграциями (Flyway или свои, с таблицей версий). Ручной `ALTER TABLE` в проде — не план.
- Бэкап перед миграцией. Всегда.
- Транзакции для любых операций с ценностями. Дюп рождается между двумя `save()`.

```java
try (Connection conn = dataSource.getConnection()) {
    conn.setAutoCommit(false);
    try {
        withdraw(conn, buyer, price);
        deposit(conn, seller, price);
        conn.commit();
    } catch (SQLException e) {
        conn.rollback();
        throw e;
    }
}
```

- Периодическое автосохранение + сохранение по значимым событиям. Не полагайся на `onDisable`.
- Идемпотентность: повторная выдача награды после краша не должна удваивать её. Ключ операции + проверка.

## 7. Производительность

### Порядок действий. Нарушение = потерянное время

1. **Измерь.** Spark: `/spark profiler start --timeout 300`, `--alloc` для аллокаций, `/spark tps`, `/spark healthreport`.
2. **Найди реальный горячий путь.** Интуиция про производительность ошибается почти всегда.
3. **Почини одну вещь.** Померь снова. Без цифр «до/после» оптимизации не было — была правка.

### Что действительно даёт выигрыш

**Убрать работу из тика.** Лучший цикл — тот, который не выполняется. Кешируй и инвалидируй по событию, а не пересчитывай каждый тик.

**Структуры данных под задачу.**

```java
// плохо — O(n) на каждый вызов, в тике
players.stream().filter(p -> p.getUniqueId().equals(id)).findFirst();

// хорошо — O(1)
sessions.get(id);
```

`LinkedList` не нужен никогда. Для примитивов на больших объёмах — fastutil (`Long2ObjectOpenHashMap`, `LongOpenHashSet`): нет боксинга, в разы меньше мусора.

**Ключ чанка — упакованный `long`:**

```java
long key = ((long) chunkX << 32) | (chunkZ & 0xFFFFFFFFL);
```

Не `"x:z"` и не `new ChunkKey(...)` в цикле.

**Никаких `getNearbyEntities` в тике.** Пространственный индекс или подписка на события входа/выхода.

**Батчинг.** Одна задача на 400 сущностей, а не 400 задач по одной. `runTaskTimer` с периодом 1 — почти всегда ошибка проектирования; 5, 20, 100 тиков обычно достаточно. Распределяй нагрузку по тикам: обрабатывай 1/20 списка каждый тик вместо всего списка раз в секунду.

**Аллокации в hot path.** Не создавай `Location`, `ItemStack`, `Component`, лямбду с захватом каждый тик. `Component` иммутабелен — собери один раз, храни в поле.

**Async-чанки:** `getChunkAtAsync`, никогда синхронной загрузки по координатам игрока.

**I/O — никогда в main thread.** Ни файл, ни JDBC, ни HTTP, ни DNS-резолв.

### Чего не делать
- Микрооптимизации без профиля (`i++` vs `++i`, ручной unroll) — шум, JIT это съест.
- Кеш без стратегии инвалидации — уже утечка, просто ещё не заметная. Ставь TTL и максимальный размер (Caffeine).
- `System.gc()`, GC-флаги из кода плагина, свои пулы потоков без ограничения размера.
- Замена читаемого стрима на цикл «ради скорости» вне hot path. Escape-анализ сильнее твоей интуиции.
- Оптимизация того, что выполняется раз в минуту.

### Бюджет тика
50 мс на тик — весь сервер. Твой плагин на нагруженном сервере имеет право примерно на 1–2 мс. Если один твой обработчик стабильно занимает 5 мс — он архитектурно неправ, а не «немного медленный».

## 8. Конкурентность и Folia

- Bukkit API **не** потокобезопасен. Всё, что трогает мир, сущностей, инвентари — main thread.
- I/O, HTTP, тяжёлые вычисления — async, всегда. Возврат в main:

```java
CompletableFuture
    .supplyAsync(() -> repository.load(id), ioExecutor)
    .thenAcceptAsync(profile -> applyToPlayer(player, profile), mainExecutor);
```

- Не блокируй main через `.join()` / `.get()`. Это фриз сервера, а не «маленькая пауза».
- Общие структуры между потоками — `ConcurrentHashMap`, иммутабельные снимки или явные локи. `synchronized` вокруг всего — не решение, а будущий дедлок.
- После async-возврата **перепроверь актуальность**: игрок мог выйти, мир — выгрузиться.

```java
Player online = Bukkit.getPlayer(id);
if (online == null || !online.isOnline()) return;
```

**Folia.** Единого main thread нет: есть региональные и сущностные шедулеры. Пиши сразу через абстракцию:

```java
public interface Scheduler {
    void runAt(Location location, Runnable task);
    void runFor(Entity entity, Runnable task);
    void runAsync(Runnable task);
}
```

Две реализации — Paper и Folia. Ретрофит после написания всего проекта стоит в разы дороже.

## 9. Конфиги и тексты

### Конфиг читает человек

- Пустые строки между смысловыми блоками, короткая шапка секции.
- Значения по умолчанию — рабочие из коробки.
- Комментарии в конфиге **нужны**, в отличие от кода: пользователь не читает исходники. Объясняй единицы, диапазон, последствия.
- Ключи `kebab-case`, единообразно. Единица измерения в имени: `cooldown-seconds`, `save-interval-minutes`. Голое `20` — тики или секунды, не угадать.
- Версия конфига + автомиграция. Ломать чужие настройки апдейтом — неуважение.
- Сообщения — **всегда** отдельный `messages.yml`. Хардкод строк в Java запрещён.

```yaml
# config-version меняется только разработчиком. Не трогайте.
config-version: 3

# Экономика. Баланс хранится с точностью до 2 знаков.
economy:
  # Стартовый баланс новичка.
  starting-balance: 100.0

  # Максимум на счету. 0 — без ограничения.
  balance-cap: 0.0

  # Как часто данные сбрасываются на диск.
  # Меньше — безопаснее при краше, больше — меньше нагрузка на БД.
  save-interval-minutes: 5

storage:
  # sqlite | mysql
  type: sqlite

  # Только для mysql. Пароль лучше вынести в secrets.yml.
  mysql:
    host: localhost
    port: 3306
    database: shop
    pool-size: 6
```

### Конфиг в коде — типизированный

```java
public record EconomyConfig(
    double startingBalance,
    double balanceCap,
    Duration saveInterval
) {
    public EconomyConfig {
        if (startingBalance < 0) throw new ConfigException("economy.starting-balance должен быть >= 0");
    }
}
```

Читается один раз при загрузке. Не `config.getDouble("economy.starting-balance")` в тике.

### Игровые тексты

- **MiniMessage**, не `&`-коды и не `§`.
- Плейсхолдеры именованные: `<player>`, `<amount>`. Не `{0}`, не `%s`.
- Пиши как живой человек, не как системное уведомление:

```yaml
# плохо
error-no-money: "&c&lERROR! &cInsufficient funds!!! Transaction failed!"

# хорошо
not-enough-money: "Не хватает <red><amount></red> монет."
region-occupied: "Здесь уже есть регион. Выбери точку дальше 50 блоков от спавна."
```

- Ошибка говорит, **что делать дальше**, а не только что всё плохо.
- Единый тон: либо «ты», либо «вы». Решается один раз на проект.
- Без КАПСА, без цепочек восклицательных знаков, без эмодзи-спама. Максимум один смысловой префикс, определённый в одном месте и не продублированный в каждой строке.
- Числа и время форматируются для человека: `1 234 монеты`, `2 мин 30 с`. Не `1234.0`, не `150000ms`.
- Склонения: `1 монета / 2 монеты / 5 монет` — сделай хелпер один раз, это заметно.
- Логи **не** переводятся: английский, стабильные формулировки, grep-friendly, с контекстом.

## 10. Ошибки, логи, отладка

### Исключения
- Не глотай. `catch (Exception ignored) {}` — бомба замедленного действия.
- Не лови `NullPointerException` — устрани причину.
- Лови конкретный тип, а не `Exception`, если знаешь, что может прилететь.
- Оборачивай границы (обработчик события, тик задачи), чтобы одна ошибка не валила весь тик.

```java
// плохо
catch (Exception e) {
    e.printStackTrace();
}

// хорошо
catch (SQLException e) {
    logger.warn("Failed to save profile player={} world={}", id, worldName, e);
    messages.send(player, "storage.save-failed");
}
```

### Логи
- Логируй **решения**, а не поток: «отказано, причина X», не «вошёл в метод».
- Всегда с контекстом: `player=`, `world=`, `region=`, `amount=`.
- Уровни осмысленно: `ERROR` — сломано и требует человека; `WARN` — подозрительно, но пережили; `INFO` — важные события жизненного цикла, редко; `DEBUG` — за флагом конфига, выключен по умолчанию.
- Никаких `System.out.println`. Только логгер плагина.
- Не логируй токены, пароли, IP, приватные данные.
- Не спамь в лог на каждый тик — админ перестанет читать логи вообще, включая важные.

### Отладка
- Воспроизведи минимальным сценарием, прежде чем чинить.
- Читай stacktrace целиком, включая `Caused by`.
- Ошибка «в чужом плагине» в 9 случаях из 10 — твой аргумент, дошедший до чужого кода.
- Каждый найденный в проде баг → регрессионный тест. Иначе он вернётся.

## 11. Тестирование

Тестируется в первую очередь то, что в `domain/` — там нет Bukkit, значит тесты быстрые.

```java
@Test
void withdrawFailsWhenBalanceInsufficient() {
    Account account = new Account(UUID.randomUUID(), BigDecimal.valueOf(10));

    assertThatThrownBy(() -> account.withdraw(BigDecimal.valueOf(25)))
        .isInstanceOf(InsufficientFundsException.class);

    assertThat(account.balance()).isEqualByComparingTo("10");
}
```

- JUnit 5 + AssertJ для логики: цены, кулдауны, права, парсинг, форматирование.
- MockBukkit — точечно, для взаимодействия с API. Не строй на нём весь набор тестов.
- Тестируй **границы**: 0, отрицательное, максимум, пустая строка, `null`, дубликат, конкурентный вызов.
- Property-based (jqwik) для формул и сериализации — находит то, что не придумаешь руками.
- Имя теста — предложение о поведении: `refundRestoresBalanceAfterCancelledPurchase`. Не `test1`, не `testWithdraw`.
- Не тестируй геттеры и мапперы ради процента покрытия. Покрытие — метрика, а не цель.
- Ручной сценарий перед релизом: чистая установка, обновление со старой версии, перезагрузка, выход игрока в момент операции.

## 12. Сборка, зависимости, CI

- **Reproducible build:** зафиксированные версии, никаких `latest` и динамических диапазонов.
- **Не шейди** то, что уже на сервере: Adventure, Gson, Guava, SnakeYAML. Конфликт классов ломает чужие плагины.
- Шейдишь остальное — обязательно `relocate` в свой пакет.
- Минимизируй зависимости. Каждая — это CVE, конфликт версий и +200 КБ.
- `paper-plugin.yml` с честным `api-version`, корректными `depend` / `softdepend`, без лишних прав в `permissions`.
- SemVer: ломающее изменение публичного API — мажорная версия.

**CI как минимум:**
1. `./gradlew build` на чистом клоне.
2. Spotless check — сборка падает при нарушении форматирования.
3. ErrorProne / NullAway.
4. Тесты.
5. OWASP Dependency-Check на известные CVE.
6. Артефакт с версией и коммит-хешем в манифесте — чтобы по джару понять, что внутри.

Красный CI не мёржится. Исключений нет.

## 13. Безопасность

### Ввод — враждебен всегда

- Проверяй длину, диапазон, символы, кодировку. Всё, что пришло от игрока.
- SQL **только** через `PreparedStatement`. Конкатенация — уязвимость, а не стиль.
- Имена файлов из ввода: нормализуй путь и проверь, что он внутри `dataFolder`.

```java
Path target = dataFolder.resolve(name).normalize();
if (!target.startsWith(dataFolder)) throw new SecurityException("path traversal: " + name);
```

- Никакой десериализации недоверенных данных: `ObjectInputStream`, `BukkitObjectInputStream` из чужого источника, YAML с произвольными тегами.
- Лимиты на всё: длина строки, страницы книги, размер стека, число сущностей при спавне, глубина вложенности JSON. Иначе сервер крашат через твой плагин.
- MiniMessage из пользовательского ввода — только с ограниченным набором тегов. Иначе игрок вставит `<click:run_command>`.

### Права и игровая логика

- Проверка прав — на сервере, в обработчике, перед действием. Скрытая кнопка GUI проверкой не является.
- Не доверяй клиенту: слот, координаты, содержимое инвентаря, скорость движения приходят от клиента.
- Атомарность операций с ценностями: списание и выдача в одной транзакции. Между ними рождается дюп.
- Rate limit на дорогие команды и на клики в GUI.
- Никогда не вызывай `setOp` из кода и не обходи проверки прав «для удобства».
- Аудит-лог значимых действий (выдача предметов, изменение баланса, админ-команды) — отдельно, с меткой времени и исполнителем.

### Секреты и сеть

- Токены и пароли — не в git. Отдельный файл + `.gitignore`, или переменные окружения.
- HTTPS с валидацией сертификата. Таймауты на подключение и чтение обязательны.
- Ограничивай размер ответа — иначе OOM от чужого сервера.
- Не выполняй код, полученный по сети. Никогда. Ни в каком виде.
- Регулярно обновляй зависимости.

### Устойчивость

- Деградируй мягко: БД недоступна → read-only режим с понятным сообщением, а не NPE каждому игроку.
- Circuit breaker на внешние сервисы: три таймаута подряд → пауза, а не бесконечные попытки.
- Исключение в одном обработчике не должно ронять тик.

## 14. Читабельность и стиль

- Читатель важнее писателя: код читают в 10 раз чаще, чем пишут.
- Форматирование автоматическое (Spotless). Споры о стиле в ревью запрещены.
- Порядок в классе: константы → поля → конструктор → публичные методы → приватные. Приватный метод сразу после того, кто его вызывает.
- Строка ~120 символов, перенос по смыслу, а не по счётчику.
- Пустая строка отделяет смысловые блоки внутри метода. Три подряд — нет.
- Вложенность максимум 3 уровня, дальше — извлекай метод.
- Метод обычно 5–25 строк. Не «ровно 10» и не «страница кода».
- `final` для неизменяемых полей — документация, встроенная в компилятор.
- `record` для DTO и value-объектов.
- `sealed interface` + pattern matching вместо цепочки `instanceof`:

```java
sealed interface PurchaseResult {
    record Success(Transaction tx) implements PurchaseResult {}
    record NotEnoughMoney(BigDecimal missing) implements PurchaseResult {}
    record InventoryFull() implements PurchaseResult {}
}

switch (result) {
    case Success s -> messages.send(player, "shop.bought", s.tx());
    case NotEnoughMoney n -> messages.send(player, "shop.not-enough", n.missing());
    case InventoryFull ignored -> messages.send(player, "shop.inventory-full");
}
```

Компилятор проверит полноту. Добавишь новый вариант — узнаешь сразу, а не в проде.

- Одна идея на строку. `if (a) { doX(); }` в одну строку — экономия, которая стоит багов.
- Не сокращай имена: `transaction`, а не `txn`, `trns`, `t`. Исключение — общепринятые счётчики `i`, `x`, `z`.
- Магические числа — в именованные константы: `MAX_STACK_SIZE`, `COOLDOWN_TICKS`.

## 15. Совместимость и публичное API

- Даёшь API другим плагинам — выделяй модуль `-api`. Внутренности не попадают в него никогда.
- Публичное API стабильно: депрекейт с одним релизом форы и указанием замены.
- Свои события наследуй от `Event`, делай `Cancellable`, только если отмена осмысленна. Вызывай их **до** совершения действия, а не после.
- Регистрируй сервисы через `ServicesManager` — так тебя найдут корректно.
- Уважай чужие отмены событий, WorldGuard-флаги, Vault-провайдеры, права других плагинов.
- Не ломай мир соседей: не отменяй чужие события в `MONITOR`, не переопределяй чужие команды молча.
- bStats — без персональных данных и с возможностью отключить.
- Проверяй обновление на реальных данных: старый конфиг + старая БД + новый джар.

## 16. Каталог антипаттернов

| Антипаттерн | Чем плохо | Как правильно |
|---|---|---|
| `Map<Player, X>` в поле | утечка памяти | `Map<UUID, X>` + очистка на quit |
| `runTaskTimer(this, 0, 1)` | 20 срабатываний/с без нужды | больший период, батчинг |
| `getNearbyEntities` в тике | O(n) по чанкам | пространственный индекс, события |
| Строковый ключ чанка | мусор и медленный хеш | упакованный `long` |
| `catch (Exception ignored)` | скрытые баги | лог с контекстом или проброс |
| Конкатенация SQL | инъекция | `PreparedStatement` |
| Проверка меню по заголовку | подделывается | `InventoryHolder` |
| Хардкод текста в Java | нельзя перевести и изменить | `messages.yml` |
| `config.getX()` в тике | парсинг YAML в hot path | загрузка в record при старте |
| `.join()` в main | фриз сервера | `thenAcceptAsync` в main-executor |
| Шейд Adventure/Guava | конфликт классов | не шейдить, либо relocate |
| Статический `getInstance()` везде | скрытый граф зависимостей, нет тестов | конструктор |
| `Utils`, `Manager`, `Helper` | нет ответственности | имя по домену |
| Кеш без TTL | утечка | Caffeine с лимитом и TTL |
| Комментарий-пересказ | шум, устаревает | переименование, удаление |
| Интерфейс с одной реализацией «на будущее» | лишний слой | конкретный класс |
| Синхронная загрузка чанка | лаг-спайк | `getChunkAtAsync` |
| `onDisable` как единственное сохранение | потеря данных при краше | периодический flush |
| Логика в `onEnable` на 300 строк | нечитаемо, не тестируется | сервисы + проводка |
| NMS напрямую в 12 классах | смерть при обновлении | мост за интерфейсом |

## 17. Рубрика ревью

Ревьюер проверяет по порядку. Первое найденное «нет» — уже повод для обсуждения.

**Корректность**
- Все вызванные методы API существуют в целевой версии?
- Границы значений обработаны: 0, отрицательное, максимум, пусто, `null`?
- Что произойдёт, если игрок выйдет в середине операции?
- Есть ли путь, на котором данные сохранятся дважды или не сохранятся?

**Потоки**
- Ничего Bukkit-специфичного не вызывается из async?
- Ничего блокирующего не вызывается из main?
- Общие структуры защищены?

**Производительность**
- Что здесь выполняется чаще 20 раз в секунду?
- Есть ли аллокации или линейный поиск в hot path?
- Профиль снят, если менялся горячий код?

**Чистота**
- Есть ли комментарии, пересказывающие код?
- Есть ли мёртвый код и «на будущее»?
- Имена говорят о домене?

**Безопасность**
- Ввод валидируется на границе?
- Права проверены на сервере перед действием?
- Операции с ценностями атомарны?

**Ревью читает не только добавленное, но и удалённое.**
